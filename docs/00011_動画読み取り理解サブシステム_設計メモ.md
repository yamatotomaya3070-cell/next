- 対象（新規）: `src/lib/video/analysis/`、`scripts/video/analyze-*.ts`、`supabase/migrations/00011_video_ingests_analysis.sql`（提案版・未作成）

- 背景: 2026-07-27のヒアリング（実施済み）で「現状の合成動画と実案件のクオリティ差が大きすぎる。動画のレベルを上げる必要がある」との要望が出た。品質差は **①生成エンジン側で根本的に直すもの** と **②実動画を読み取らないと直せないもの** に分かれる。本メモは、その結論を受けて **②の『動画読み取り（解析・理解）』サブシステム** を設計する。

## 1. 【第一の仕分け】根本解決 vs 動画読み取りで解決

ヒアリングで出た「レベルを上げる」要望を、実装の観点で切り分けたもの。

### バケット① 根本的に解決するもの（＝生成/合成エンジン側。読み取りでは直らない）

実動画をいくら読んでも、**作り方**を変えないと埋まらない品質差。

| 品質差 | 根本原因 | 解決策（読み取りとは別軸） |
|---|---|---|
| 音声が不自然 | Windows SAPI 合成音声 | VOICEVOX / クラウドTTSへ差し替え（`docs/00003 §5` で既定路線） |
| 映像が合成（スライド・立ち絵）で実写でない | ffmpeg合成生成そのもの | 実写素材ライブラリの導入、または実写素材の直接採用 |
| テロップ/トランジション/BGM・SEの表現が単調 | レンダリングの表現力 | render層の機能拡張（テンプレート `subtitleStyle` の拡充等） |
| 会話・ナレーションの自然さ | 台本生成モデルの限界 | 生成モデル/プロンプト改善（一部はバケット②の学習で底上げ） |

→ **読み取りサブシステムのスコープ外**。ただし②の抽出結果が「目標値」を与えるので方向づけには効く。

### バケット② 動画の読み取りでしか解決できないもの（＝本メモのスコープ）

"正しい編集"や"実務のテンポ"は、実動画を解析しないと **正解データ化も学習もできない**。

| 品質差 | なぜ読み取りが必須か | 本メモでの解 |
|---|---|---|
| 実写素材を練習に使えない（答え合わせ用データが作れない） | 実写には台本副産物の正解データが無い | 解析で `TemplateAnswerData` を **自動生成**（§4 S4） |
| カット/キープ区間の"内容"の正しさを採点できない | 提出物の中身を機械が読めない | ASR+シーン検出+動画理解で **内容ベース検品** に拡張（§5 Loop B） |
| 生成される練習案件のテンポ・テロップ量・構成が実務とズレる | 実案件の編集パターンを学んでいない | 抽出メタをRAG/生成プロンプトへ（§5 Loop A） |
| 難易度1〜5が実データ根拠を持たない | 実案件の分布を見ていない | 抽出パターンで難易度/テンプレを校正（§5 Loop C） |

## 2. サブシステムの位置づけ（全体像）

```
実案件フォルダ / ストック実写 / 提出物
        │
        ▼
┌─────────────────────────────────────────────┐
│  動画読み取り（analysis）  ← 本メモ            │
│  S0 復号・分解 → S1 音声(ASR) → S2 映像(シーン/OCR)│
│  → S3 意味理解(Gemini動画API) → S4 正解データ化    │
│  → S5 匿名化・許諾ゲート → S6 蓄積               │
└─────────────────────────────────────────────┘
        │                    │                 │
        ▼                    ▼                 ▼
  Loop A 生成向上        Loop B 内容検品      Loop C 難易度校正
 (RAG/プロンプト)       (compare拡張)       (registry/difficulty)
```

既存の `AiProvider`（gemini/mock二重化）と同じ思想で、**`VideoUnderstandingProvider` を新設**し pipeline のインターフェイスを固定する（TTS差し替えと同じく実装は後で差し替え可能に）。

## 3. 入力の3系統

| 系統 | 中身 | 学習価値 | 主用途 |
|---|---|---|---|
| **A. 前後ペア** | 実案件の未編集フル素材 ＋ 完成見本（納品物） | 最高（"どこを削ったか"が直接得られる） | 正解データ生成・編集パターン学習 |
| **B. 完成物のみ** | 実案件の納品動画のみ | 中（構成・テンポ・テロップは読めるがカット元は推定） | 生成向上・難易度校正 |
| **C. ストック実写** | 権利クリアな素材（フィラー等を含む生素材） | 中（実写の素材動画として配布＋正解データ自動生成） | バケット①の実写化と併用 |

> 系統Aは `interview_edit` テンプレートの「raw_take.mp4 と sample.mp4 を両方持つ」構造（`docs/00007 §4`）の **実写版** と見なせる。既存の設計思想とまっすぐ接続する。

## 4. 解析パイプライン（段階）

各段は **後段ほど高コスト/要許諾** になるよう並べ、途中で止めても価値が出る構成にする。

- **S0 復号・分解**: `ffprobe`（既存 `ProbeResult` を再利用）＋フレーム抽出＋音声抽出（wav）。物理層。**判断不要・無料**。
- **S1 音声解析(ASR)**: 文字起こし＋語/文タイムスタンプ、**沈黙区間**・**フィラー**・**言い直し**検出。トーキング系のカット検出の背骨。ローカル Whisper で開始可（オフライン・無料）。
- **S2 映像解析**: シーン/ショット切替検出（PySceneDetect or ffmpeg `select='gt(scene,...)'`）、テロップの有無・位置（OCR）、話者切替。
- **S3 意味理解**: Gemini 動画理解（Files API に動画アップロード→multimodal 生成）で「各区間は何をしているか／削るべきか／テロップに何を出すか」を構造化。**ヒアリング資料 §1.5 の×項目『内容ベース判定』の本体**。要APIコスト・要モデル選定（`gemini-2.0-flash` が動画対応か要検証。未対応なら動画対応モデルに分岐）。
- **S4 正解データ化**: S1–S3を統合し既存 `TemplateAnswerData` ＋ 拡張フィールドを生成（§6）。
- **S5 匿名化・許諾ゲート**: 顔・ロゴ・店名の検出とマスキング（**映像は現状ノーガード**）。職員承認。実案件は許諾フラグ必須（§7）。
- **S6 蓄積**: 構造化メタ(テキスト)→ナレッジ/RAG、正解データ→ `material_answers`（既存の職員専用RLS）、動画本体→ `materials`（許諾済みのみ）。

**フォールバック方針（既存踏襲）**: `VideoUnderstandingProvider` は gemini 実装が失敗したら mock（S0/S1のローカル解析のみで決定的に近似）へフォールバックし、`provider` 名で判別可能にする（`src/lib/ai/index.ts` と同じパターン）。

## 5. 既存資産へのフィードバック（3ループ）

- **Loop A（生成向上・テキスト経路）**: S6のメタ（平均カット率・1分あたりテロップ数・シーン構成・冒頭掴みの型 等）を `GenerateTaskInput.knowledgeContext` / `GenerateSimilarCaseInput.referenceSnippets` に注入。**今の「スキルタグ一致で最大5件」簡易版を、実測パターン注入に格上げ**。台本が実務のテンポに寄る。
- **Loop B（内容検品）**: S4の `contentCutRanges` を用い、提出物を同じ解析にかけて「削るべき区間が残っていないか」「必要テロップが入っているか」を判定。`compareProbeToAnswer` を **物理チェックはそのまま／内容チェックを追加** する形で拡張（後方互換）。
- **Loop C（難易度・テンプレ校正）**: 抽出パターンの分布から `registry.ts` の `defaultDifficulty`・`traineeTasks`・`gradingCriteria`・`toleranceSec` を実データで校正。難易度1〜5に実務的根拠を与える。

## 6. データモデル

### 6-1. 新規型（`src/lib/video/analysis/types.ts`・案）

```ts
export type VideoSourceKind = "synthetic" | "ingested_pair" | "ingested_final" | "stock";

/** 1本の動画を読み取った構造化結果（テンプレート非依存の共通形） */
export interface VideoAnalysis {
  sourceKind: VideoSourceKind;
  probe: ProbeResult;                 // S0（既存型を再利用）
  transcript: TranscriptSegment[];    // S1: 文字起こし＋タイムスタンプ
  silences: TimeRange[];              // S1: 沈黙区間
  fillers: TimeRange[];               // S1: フィラー/言い直し（cut候補）
  shots: TimeRange[];                 // S2: シーン/ショット境界
  onScreenText: OcrSpan[];            // S2: テロップ（内容・位置・区間）
  contentCutRanges: TimeRange[];      // S3: 内容として"削るべき"区間
  targetTelops: TargetTelop[];        // S3: 入れるべきテロップ（内容＋出すべき区間）
  summary: string;                    // S3: 動画内容の自然言語要約（職員向け）
  editingPattern: EditingPattern;     // Loop C 用（カット率・テロップ密度・構成型 等）
  provider: "gemini" | "mock" | "mock(fallback)";
}
```

（`TimeRange = { startSec; endSec }`。既存の命名規約に合わせ camelCase・秒単位。）

### 6-2. `TemplateAnswerData` 拡張（後方互換・任意フィールド）

```ts
// 既存フィールドは不変。以下を optional 追加：
sourceKind?: VideoSourceKind;        // 既定は "synthetic"（既存ジョブ互換）
contentCutRanges?: TimeRange[];      // 内容ベース検品用
targetTelops?: TargetTelop[];        // テロップ課題の内容採点用
```

optional にすることで、既存の合成パイプラインが生成する答えデータ・完了済みジョブとの後方互換を保つ（`docs/00007 §5` の template_type 既定値と同じ配慮）。

### 6-3. DB（`00011_video_ingests_analysis.sql`・提案版／未作成）

`docs/00003` の **原文とマスク済みを物理分離** した思想を踏襲：

| テーブル | 役割 | RLS |
|---|---|---|
| `video_ingests` | 取り込み原本・**許諾状態**・匿名化状態・sourceKind。原本パスは職員のみ | 職員のみ |
| `video_analyses` | 構造化結果（`VideoAnalysis`）。匿名化済みメタのみ | 職員のみ（正解漏洩防止） |

## 7. 匿名化・許諾ゲート（映像特有の重大リスク）

- **映像は現状ノーガード**: テキスト匿名化（正規表現）では顔・ロゴ・看板・店名を除去できない。S5で検出→ぼかし/カット、除去しきれない点は `riskNotes` として職員承認画面に必須表示（`docs/00003 §2` のテキスト匿名化と同じ運用）。
- **許諾フラグ必須**: 実案件動画（系統A/B）は依頼者の同意がないと **配布も学習利用も不可**。`video_ingests.consent_status` が `approved` でないと S6 の配布・RAG 投入をブロック。→ ヒアリングで **実案件動画の利用が許諾前提で承認済**（§10）。よって S5 の許諾ゲートは必須要件。
- ストック実写（系統C）は権利クリアを前提に許諾ゲートを簡略化できる。

## 8. 段階導入とコスト・ヒアリング対応

| フェーズ | 内容 | コスト | 要判断 |
|---|---|---|---|
| **R0** | S0+S1（ffprobe＋ローカルWhisper沈黙/フィラー検出）→ 既存 `TemplateAnswerData` を **音声解析由来** でも作れるように。`interview_edit` で内容ベース検品の第一歩 | ほぼ無料・ローカル | **判断不要**（すぐ着手可） |
| **R1** | S2（シーン検出＋OCR）→ テロップ/カット構造。Loop C の校正データ収集開始 | 低（ローカル） | 判断不要 |
| **R2** | S3（Gemini動画理解）＋実案件取り込み・匿名化・RAG本体。内容採点の本稼働 | 要APIコスト | **承認済**（予算確保・実案件動画利用OK。§10） |

> R0/R1 は **難易度設計と独立** に着手して価値が出る。R2 は予算・実案件利用ともにヒアリングで承認済みのため、R0→R1→R2 と順に実装して問題ない。難易度は1〜5のまま（Loop C は数字難易度へのマッピング）。

## 10. ヒアリング確定事項（2026-07-27・本設計の前提）

| # | 論点 | 決定 | 本設計への影響 |
|---|---|---|---|

## 11. まとめ（この設計が埋めるもの／埋めないもの）

- 埋める（②）: 実写を練習に使うための **正解データ自動生成**、**内容ベース検品**、実案件パターンによる **生成・難易度の実務化**。
- 埋めない（①）: 音声/映像の **見た目・音の質そのもの**（TTS・実写素材・render表現）。これは別軸で根本対応が必要。
- 最小の一歩: **R0（ffprobe＋ローカルWhisper）** から。判断待ち・追加コストなしで、内容検品と実写取り込みの土台になる。
