> 金融教育YouTube（NISA・投資・節約・税金・家計・資産形成・制度）を100本以上、8〜12分で継続制作する「チャンネルの顔」2名を確定する。
>
> **アオ／ミドリは廃止。以後、初心者＝ハル（`haru`）／解説＝ミナ先生（`mina`）で固定。** 03・04 の話者名アオ／ミドリはこの2名に読み替える（04のSCENE schema例・TTSキットは更新済み）。
>
> 最終目的は「綺麗なキャラ画像を作ること」ではなく **「ハルとミナ先生を使った動画を、初心者が10分自然に見続けられること」**。キャラは主役ではなく“難しい金融を分かりやすくする案内役”。実装・DB・migration は未変更（本書は設計提案）。

## 1. 現在のキャラクター生成フロー（コード事実）

```
style_guides.content.characters[]  (最大4体 / key・name・role・appearance・voiceProfile・seed・subtitleColor)
        │  style-guide/schema.ts:28-38, 73(MAX_CHARACTERS=4)
        ▼
[職員UI] CharacterAssetsPanel → generateCharacterAssetsAction  (characterAssets.ts:29)
        │  getActiveStyleGuide() → 各キャラ×全表情を生成
        ▼
generateCharacterExpressionSet  (image-gen/index.ts)
        │  ① normal を base として text-to-image で1枚生成
        │  ② 他表情は base画像を inline_data で参照する image-to-image（一貫性担保）
        │     gemini.ts:71-76 / buildPrompt: artStyle・appearance・expression・palette・seed・negativeStyle (gemini.ts:39-55)
        │     model = gemini-2.5-flash-image / 未設定・失敗時は mock=SVGプレースホルダ
        ▼
Storage "character-assets" バケットへ upload  (path = {styleGuideId}/{characterKey}_{expression}.png ; PNG固定)
        │  character-assets/schema.ts:46-52
        ▼
character_assets へ upsert  (unique(style_guide_id, character_key, expression) / 00015)
        列: style_guide_id, character_key, expression, seed, storage_path, mime_type, provider
```

**現状の特徴（事実）**
- 表情は **4種固定**：`normal / happy / surprised / thinking`（`STYLE_GUIDE_EXPRESSIONS`, schema.ts:18）。この enum は schema・image-gen・character_assets・グルーピングが共有。
- 一貫性は「数値seed（テキストアンカー）＋ base(normal)画像を参照する image-to-image」の2段構え（gemini.ts:5-9）。公開APIに数値seedパラメータが無いため、**実質の一貫性は“参照画像”が担う**。
- `appearance` は **1本の自由文字列**（構造化されていない）。`negativeStyle` も1本の文字列。
- **pose の概念が存在しない**（テーブル・storage_path・生成入力すべてに pose 無し）。
- **MASTORロック／承認の概念が無い**：`generateCharacterAssetsAction` は upsert で上書き再生成。原本を選んで固定する流れも、承認済みだけを使う仕組みも無い。character_assets は「生成画像の置き場」であって「承認済みライブラリ」ではない。

## 2. ハル／ミナを現在の仕組みに入れた場合の問題

| # | 問題 | 影響 |
|---|------|------|
| P-1 | **表情4種固定**（normal/happy/surprised/thinking）だが、ハルは7種・ミナは7種（後述）を要求 | enum拡張が schema/image-gen/character-assets/UI に波及。キャラごとに表情セットが違う点も未対応 |
| P-2 | **pose 次元が無い** | 「指し示す・説明・うなずき」等の演出（会話→図解の切替）ができない。unique制約・storage_path・生成入力すべてに pose 追加が必要 |
| P-3 | **MASTERロック／承認ライブラリが無い** | 仕様のSTEP1-11（候補3案→人間選択→REFERENCE MASTERロック→差分生成→承認→承認済みのみ利用）が成立しない。upsert上書きだと「原本」が固定されず、100本で見た目がブレる最大リスク |
| P-4 | **参照が base(normal)画像のみ** | 仕様は「REFERENCE MASTER＋STYLE MASTER＋id＋expression＋pose」を毎回入力したい。今は“その回のnormal”を参照するだけで、ロックされた原本を常に参照する設計でない |
| P-5 | **appearance が1文字列** | ハル/ミナの詳細仕様（輪郭・目・眉・髪・眼鏡・衣装・色）を構造で保持できず、プロンプト品質・変更禁止項目の管理が甘くなる |
| P-6 | **STYLE MASTER（共通画風）を画像として持てない** | 2名を「同一作品に見せる」担保が artStyle 文字列のみ。スタイル参照画像を渡せるとより強い |
| P-7 | **negative が1文字列** | 仕様の詳細 negative prompt を素直に持てない |
| P-8 | 声は `voiceProfile`（話者キー）と `subtitleColor` のみ | voice の provider/emotion は 04 の SCENE.audio[] 側に委譲する前提の整理が必要 |

→ **2キャラ運用自体は可能**（MAX_CHARACTERS=4）。本質的な不足は **①表情セットの拡張 ②pose次元 ③MASTERロック＋承認ライブラリ ④ロック原本を常に参照する一貫性戦略** の4点。

## 5. STYLE MASTER（共通画風）

2名を必ず「同一作品のキャラクター」に見せるための共通スタイル定義。`style_guides.content.artStyle` に格納する想定（＋将来はスタイル参照画像も）。

**採用する画風トークン**
```
modern Japanese 2D educational animation, clean line art, clean flat colors,
soft cel shading, slightly warm illustration, simple expressive face,
friendly financial-education character, YouTube explainer animation,
professional but approachable, consistent character design, simple silhouette,
medium detail, high readability, animation-friendly design
```

**避ける方向（NEGATIVEの母体）**
```
moe anime, shonen manga, shojo manga, kids/toddler style, chibi, VTuber,
game character, social-game (gacha) art, 3DCG, photorealistic,
corporate free-stock look, overly pretty faces, heavy/dramatic shading,
complex costume, excessive accessories
```

**技術メタ（全生成共通）**
- 背景：透明（不可なら単色）。文字・ロゴ・小物・他キャラなし。
- 出力：切り抜きやすい正面〜ごく軽い3/4。PNG。
- 2名で **同じ線の太さ・同じ塗り・同じ頭身・同じ陰影**。

## 11. reference画像を使った identity consistency 戦略

Gemini画像APIに数値seedが無いため、**一貫性の本体は「参照画像」**。仕様のSTEP1-11をこの制約に合わせて具体化する。

```
STYLE MASTER（共通画風・将来はスタイル参照画像）
        +
REFERENCE MASTER（キャラごとにロックした“原本”画像 ← ここが肝）
        +
character_id + expression + pose
        ↓ image-to-image（毎回ロック原本を参照）
差分アセット（表情/ポーズ）
        ↓ 人間レビュー → 承認
character_assets（is_approved=true）＝承認済みライブラリ
```

- **STEP1** STYLE MASTER 確定（artStyle/negativeStyle）。
- **STEP2-3** ハル/ミナの MASTER候補を各3案（§6・§7、text-to-image）。
- **STEP4-5** 職員が各1案を選択 → その画像を **REFERENCE MASTER としてロック**（`is_master=true`, `is_approved=true`）。以後の原本はこれ。
- **STEP6-7** MASTERを参照に **表情差分・ポーズ差分**を image-to-image 生成（毎回“その回のnormal”ではなく**ロック原本**を参照）。
- **STEP8-9** 職員レビュー → 承認済み `character_asset` として保存。
- **STEP10** SCENEは **承認済みasset優先**（`is_approved=true` の (id, expression, pose) を取得）。
- **STEP11** 必要な差分が無い場合のみ MASTER参照で追加生成 → 承認して追加。
- **ドリフト対策**：MASTER確定後は §8 の「変更禁止」を毎プロンプトに明記＋人間レビュー必須。将来は原本との類似度チェック（画像埋め込みのコサイン類似）で自動フラグ（P2）。
- **フォールバック**：GEMINI未設定/失敗時は mock(SVGプレースホルダ)。ただし**mockは承認ライブラリに入れない**（is_approved=false のまま）＝就労者に出さない。

## 12. character_assets 変更案（既存を最大限再利用・非破壊追加）

既存の「生成画像置き場」を **「承認済みキャラクターライブラリ」** へ格上げする。追加は非破壊（新カラムは default 付き）。

**(a) `character_assets` テーブル（00015）への追加**
```sql
alter table character_assets add column pose text not null default 'front';
alter table character_assets add column kind text not null default 'expression'; -- master | expression | pose | candidate
alter table character_assets add column is_master boolean not null default false;
alter table character_assets add column is_approved boolean not null default false;
alter table character_assets add column approved_by uuid references auth.users(id);
alter table character_assets add column approved_at timestamptz;
alter table character_assets add column master_asset_id uuid references character_assets(id); -- 差分が参照した原本
-- unique を (guide, character_key, expression) → (guide, character_key, expression, pose) へ拡張
alter table character_assets drop constraint character_assets_style_guide_id_character_key_expression_key;
create unique index character_assets_uni
  on character_assets(style_guide_id, character_key, expression, pose) where is_approved;
```
- storage_path を `{guide}/{characterKey}_{expression}_{pose}.png` に拡張（`characterAssetStoragePath` を pose 対応に）。
- **承認済みのみ unique**＝候補は複数持てる（3案比較）、選ばれた1つを承認。

**(b) 表情セットをキャラ別に**（現行 `STYLE_GUIDE_EXPRESSIONS` 4固定を拡張）
- `StyleGuideCharacter` に任意フィールドを追加（非破壊）：
```ts
expressions?: string[];  // 例: haru=[neutral,curious,surprised,worried,thinking,understood,happy]
poses?: string[];        // 例: [front,three_quarter_left,...]
appearanceStructured?: { outline; eyes; brows; hair; hairColor; body; head; outfit; outfitColor; glasses?; color };
```
- enum を「固定4種」から「キャラの `expressions` を正とし、未指定時のみ既定セット」に緩める。`normal`→`neutral` へ用語統一（マイグレーションで別名許容）。

**(c) `negativeStyle`** はガイド共通の詳細negative（§10）を保持できるよう、そのまま長文文字列で運用（構造化不要）。

## 13. SCENE との接続案

04 の SCENE.audio[] / visual と接続する。

- **話者**：`SCENE.audio[].speaker = character_id`（`haru` / `mina` / `narrator`）。
- **表情の決定**：`audio[].emotion → expression` をキャラ別マップで解決（下表）。SCENE側に個別の `character_expression` は持たず emotion から導出（04の設計判断どおり）。
- **ポーズの決定**：役割ルール — 話者かつ図解を指す＝`pointing`/`explaining`、聞き役＝`nodding`/`thinking`、驚き＝`surprised`、既定＝`front`（相手側へ軽い3/4）。
- **アセット解決**：`(character_id, expression, pose)` で `character_assets(is_approved)` から取得。無ければ `pose=front` へフォールバック＋「要生成」フラグ（STEP11へ）。
- **色**：字幕/テロップは `character.subtitleColor`（ハル青・ミナ緑）。非話者は減光（既存 render の思想）。

**emotion → expression マップ**
| audio.emotion（04 §4） | haru | mina |
|---|---|---|
| neutral | neutral | neutral |
| curious / question_naive | curious | — |
| surprise / positive_surprise | surprised | — |
| worried / doubt | worried | — |
| realization / understood | understood | — |
| happy / bright | happy | positive |
| calm_warm / explain_calm | neutral | explaining |
| pointing（図解誘導） | — | pointing |
| caution / gentle_warning | worried | caution |
| reassuring / empathy | neutral | reassuring |
| thinking | thinking | thinking |

**基本リズム（§10-11 の会話演出）**：ハルが疑問(worried/curious) → ミナが短く回答(explaining/caution) → **図解へ切替（会話で完結させない）** → 数字・比較 → ハルが理解(understood)/追加質問 → 次の説明。キャラ中心画面は全体の20〜30%目安（内容優先）。数字・制度・比較・複利・グラフ・タイムライン・手順は**キャラを外して図解**（04の図解PoCで実証済み）。

## 15. P0 / P1 / P2 改修案

### P0 — ハル/ミナが「チャンネルの顔」として成立する最小
- `style_guides` に **haru/mina を定義**（2キャラ・BLUE/GREEN・§3/§4の詳細appearance・subtitleColor・voiceProfile）。STYLE MASTER＝artStyle/negativeStyle を §5/§10 で確定。
